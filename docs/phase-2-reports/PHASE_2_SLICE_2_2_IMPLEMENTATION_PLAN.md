## 4. Schema relationship diagram

Text diagram. `──<` means "one to many"; `RESTRICT` applies to every update and delete rule. Mermaid is not used because rendering is not verified (validation item V-5 in the data-model document).

```text
organizations (id)
  ├──< memberships (id, organization_id, user_id, role, status, ...)
  │       UNIQUE (organization_id, user_id)   ← also referenced by sessions
  ├──< properties (id, organization_id, code, name, ...)
  │       UNIQUE (id, organization_id)
  │       └──< floors (id, organization_id, property_id, ...)
  │               FK (property_id, organization_id) → properties (id, organization_id)
  │               UNIQUE (id, property_id, organization_id)
  │               └──< rooms (id, organization_id, property_id, floor_id, ...)
  │                       FK (floor_id, property_id, organization_id) → floors (id, property_id, organization_id)
  │                       UNIQUE (id, property_id, organization_id)
  │                       └──< beds (id, organization_id, property_id, room_id, ...)
  │                               FK (room_id, property_id, organization_id) → rooms (id, property_id, organization_id)
  └──< audit_events (id, organization_id NULLABLE, actor_user_id NULLABLE, ...)

users (id, global: not tenant-owned)
  ├──< memberships           FK user_id → users (id)
  ├──< sessions (id, token_hash UNIQUE, user_id, active_organization_id NULLABLE, ...)
  │       FK (user_id, active_organization_id) → memberships (user_id, organization_id)
  │       (a NULL active organisation skips the check: PostgreSQL MATCH SIMPLE)
  └──< audit_events          FK actor_user_id → users (id)
```

**Who enforces what.** The composite keys make a cross-tenant row **unrepresentable in PostgreSQL**: floors, rooms and beds cannot point at a parent in another organisation or property, and a session cannot name an organisation its user does not belong to. Tables that are not part of that chain are _not_ protected by the database from tenant mix-ups: `audit_events` (its organisation and actor are independent foreign keys), `memberships` (single-column keys) and `users` (global). Those rely on application code.

**Common rules.** UUID keys with a database default (`gen_random_uuid()` is built in on PostgreSQL 13+, so no extension is needed; the validation database was 17.11). Timestamps are `timestamptz`. Every foreign key is `ON UPDATE RESTRICT ON DELETE RESTRICT`. Archive is a nullable `archivedAt`; there is no hard delete in the approved design. `updatedAt` is maintained by Prisma in the application, **not** by the database.

**Not decided, therefore not designed:** what archiving a parent does to its active children; whether an archived record's label can be reused (the partial unique indexes above assume yes); organisation lifecycle semantics beyond ACTIVE and DISABLED; any permission-to-role mapping (the table-driven mapping is slice 2.3, and `U-07` is the owner's decision). Anything not listed above is out of scope.

**Gate A exit:** schema drafted on a copy first (see Gate B, step B0); `prisma validate` passes with a placeholder URL; `verify_phase_scope.py` passes against the draft (S2, S6 and S7 are the likely traps; the guard is read-only); composite-key relations in F-6 either validate or the fallback is chosen; the owner has answered every ◆ item or accepted the stated default in writing.

### 8.4 Harness rules

- Database tests run only when an explicit variable names a URL that passes the same checks as `db_guard.py` (host `127.0.0.1`, port 5433, database `nook_test`). Without it they report **SKIPPED**, never passed. A CI job that has a Postgres service sets a second variable that turns a skip into a failure.
- `apps/api/test/` is outside the guard's S9 scan, but tests use the `pg` driver directly for raw SQL so that no `$queryRaw` appears anywhere under `src/`.
- Failure handling follows the earlier gates: preserve the original output and exit code, stop on a prerequisite failure, clean up only what the run created, report test and cleanup results separately.
