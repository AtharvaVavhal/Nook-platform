# Phase 2 — Slice 2.2 Isolated Throwaway PostgreSQL Test Environment (historical Revision 3 design, version 0.1)

**Status:** historical Revision 3 design only, written 2026-10-29. **Nothing in this document has been executed or implemented.** No Docker command, database connection, network probe, SQL, Prisma command, container, network, volume, database or role was touched or created. Revision 2 of the disposable-test package (manifest `30df85941c508147452655b7f8582f82a176d16a024bdc764e253e97422f51b9`) is **unchanged and preserved** as evidence; the Revision 3 package is preserved as historical tooling, while [Revision 4](disposable-test-v4/README.md) is the current package candidate. Authorization is not requested or implied.
**Companions:** [Disposable test plan (revision 2)](PHASE_2_SLICE_2_2_DISPOSABLE_TEST_PLAN.md) · [Owner review (revision 2)](OWNER_REVIEW_SLICE_2_2.md) · [Decisions for this design](OWNER_REVIEW_ISOLATED_ENVIRONMENT.md) · [Package revision 2](disposable-test/README.md).

**Revision 3 package (static only, never executed):** [`disposable-test-v3/`](disposable-test-v3/README.md), with [SAFETY.md](disposable-test-v3/SAFETY.md) and the updated [decision register](OWNER_REVIEW_ISOLATED_ENVIRONMENT.md). Where it differs from this v0.1 design, **revision 3 and its SAFETY.md prevail**. Revision 4 is the current package candidate; it does not authorize execution and supersedes this design for current planning:

- the folder is `disposable-test-v3/` (not `disposable-test-isolated/`);
- the **owner chooses the run id** and puts it in the authorization (the runner no longer generates it), and the run directory must be exactly `disposable_pg_<run id>`;
- the token also binds the three resource names and an explicit egress acknowledgement (`…;container=…;volume=…;network=…;egress=residual-risk-unresolved`);
- **`I-9` is reversed in the recommendation:** a resource that carries this run's label or name but has no matching record is **never adopted**; it is reported and needs a manual owner review;
- **host-service reachability is not blocked and is an unresolved residual risk** (new decision `I-12`); section 8 item 3 is not mitigated by anything in the package;
- the closed administrative list drops the `pg_stat_activity` read and the role-session snapshots, and adds the beacon read-back and the `pg_hba_file_rules` read; there is no `DROP` inside the cluster;
- a new `env_up` stage creates the network, volume and container, and the container is created by network **name**, not ID; the administrator environment file is deleted right after `docker create`;
- preflight refuses on **any** container, volume or network with the disposable label, this run's label or the `nook-iso-` prefix, for each of the three resource kinds;
- the identity verifier is a separate pure Node function with an offline self-test, and treats a not-running container's network details leniently (unverified Docker behaviour).

Labels: **Static** = checked by reading files, not by running anything. **Proposed** = designed, no run has confirmed it. **Unverified** = depends on Docker or PostgreSQL behaviour that has not been observed.

## 1. Why, and what changes

Revision 2 runs inside the **existing** Nook PostgreSQL container, so its two disposable roles are cluster-wide roles that probably have default `CONNECT` on `nook_dev` and `postgres`. That exposure (decision `R-1`) cannot be removed without touching protected databases, so revision 2 only _observes_ it. Option D of `R-1` removes it by design: run the same tests against a **separate, throwaway PostgreSQL container** that shares nothing with the existing one.

The effect, if the isolation conditions in section 5 hold: the disposable roles exist **only inside a cluster that contains no protected data**, the admin path targets **only that cluster**, no stage reads, inspects or depends on `nook_dev` or the existing container, and cleanup removes whole Docker resources that this run created instead of dropping objects inside a shared cluster. If any condition cannot be established, the test **stays blocked**.

## 2. The isolated environment

### 2.1 Resource identities (all new, all unique per run)

`RUNID` = `iso` + UTC timestamp + 4 random hex digits, generated by the runner, for example `iso20261030T091500Z-3fa9`.

| Resource            | Name or value                                         | How it is made unique and tied to the run                                                                                                                              |
| ------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Container           | `nook-iso-pg-<RUNID>`                                 | Absent before creation; labels `com.nook.disposable=true`, `com.nook.iso-run=<RUNID>`, `com.nook.package-manifest=<manifest hash>`; its full 64-hex **ID** is recorded |
| Volume              | `nook-iso-vol-<RUNID>`                                | Absent before creation; same labels; name, `CreatedAt` and labels recorded                                                                                             |
| Network             | `nook-iso-net-<RUNID>`                                | Absent before creation; same labels; its **ID** recorded; a dedicated bridge network, so the container shares a network with nothing                                   |
| Image               | local `postgres:17.11-alpine`, pinned by **image ID** | Created `--pull never`: no download. The image is read-only shared content, never modified or removed by this run                                                      |
| Host port           | `127.0.0.1:<ISO_PORT>` (proposal `15433`)             | Hard-coded in the package; never `5432` or `5433`; verified free before and verified as the only listener afterwards                                                   |
| Administrator       | `nook_iso_admin`, random password in a 0600 env file  | A new name and credential; the existing `nook` / placeholder credentials appear nowhere in the package                                                                 |
| Disposable roles/db | `nook_migrator_test`, `nook_app_test`, `nook_test`    | Created inside the isolated cluster only; removed with the container, not dropped inside a shared cluster                                                              |
| Beacon              | `nook.iso_run_id = <RUNID>` on database `nook_test`   | Every test connection must read it back and match the recorded run id, proving it reached the isolated database and no other server                                    |

### 2.2 What is deliberately not shared with the existing Nook environment

| Existing Nook resource (from `docker-compose.yml` and the earlier gates)                                          | In the isolated design                                                                                                 |
| ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Container `nook-postgres-1` (compose service `postgres`)                                                          | Never inspected, started, stopped, exec'd into or required. A different container is created                           |
| Volume `nook_nook_postgres_data`                                                                                  | Not mounted, not inspected as a dependency; a new volume is created. The container may have exactly one mount, its own |
| Compose default network (name inferred as `nook_default`; **unverified**)                                         | Not joined; a dedicated network is created                                                                             |
| Host port `127.0.0.1:5433` and host port `5432`                                                                   | Not used. A third port is used                                                                                         |
| Credentials `nook` / `nook_local_only` and database `nook_dev`                                                    | Not present in the package's connection logic, environment files or URLs; `nook_dev` is never queried                  |
| Other projects' containers, volumes and networks (`proofline-*`, `pf-recovery-*`, `spidosoft-*`, as seen earlier) | Not touched. Cleanup uses only IDs and names recorded by this run, with matching labels                                |
| `scripts/db_guard.py`                                                                                             | Not used: it refuses every port except 5433, and is unmodified                                                         |

## 3. Connection boundary (three classes, nothing else)

| Class                                        | Path                                                                                                                                                      | Used for                                                                                                                                 | Rules                                                                                                                                                                                                                      |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Application and test**                  | TCP to `127.0.0.1:<ISO_PORT>`, database `nook_test`, as `nook_migrator_test` or `nook_app_test`, with a password; beacon read back and matched            | schema, provisioning, inventory, all tests, drift, the adapter test                                                                      | Hard-coded host, port and database in every script. Never `5432` or `5433`, never `nook_dev`, never a remote host, never a Unix socket, never a fallback datasource, never a shadow database                               |
| **2. Admin provisioning (isolated cluster)** | `docker exec` into the **recorded isolated container only**, its local socket, maintenance database `postgres` **of that cluster**, user `nook_iso_admin` | a closed list: catalogue reads, `CREATE ROLE` ×2, `CREATE DATABASE`, `ALTER ROLE … PASSWORD` ×2, the beacon, one `pg_stat_activity` read | Every call first re-verifies the container ID and its run-id label. It cannot reach any protected database because none exists in that cluster. **Still an exception to "no Unix sockets": needs approval (decision I-4)** |
| **3. Docker lifecycle (new)**                | The Docker CLI against the local daemon, through a closed set of named operations (section 4)                                                             | create, verify, start, stop and remove this run's own network, volume, container                                                         | Every operation names a recorded ID or exact name, carries or checks the run-id label, and never uses wildcards, `prune`, `rm -f`, `kill`, `compose` or `pull`                                                             |

**Hard conditions.** All test and runtime-role connections target the isolated database. All administrative connections target only the isolated container. No test role or process receives the existing development database's credentials or URL. No stage depends on `nook_dev`, the existing cluster or port `5432`. **If any of these cannot be established, the test remains blocked** (section 5).

## 4. Lifecycle and every future command (none executed)

`<CID>`, `<NID>` and `<IMAGE_ID>` are recorded identities, not names. Commands run only inside a future, authorized run.

### 4.1 Preflight (read-only)

```text
docker context show                                        # desktop-linux or default; DOCKER_HOST/CONTEXT/CONFIG must be unset
docker info --format '{{.ServerVersion}}'                  # proves the daemon is running; the runner NEVER starts Docker
docker image inspect postgres:17.11-alpine --format '{{.Id}}'          # local only; equals the authorized <IMAGE_ID>; no pull
docker ps -a -q --filter 'label=com.nook.disposable=true'              # must be empty (no leftovers from any earlier run)
docker ps -a -q --filter 'name=nook-iso-'                              # must be empty
docker volume ls -q --filter 'label=com.nook.disposable=true'          # must be empty
docker volume ls -q --filter 'name=nook-iso-'                          # must be empty
docker network ls -q --filter 'label=com.nook.disposable=true'         # must be empty
docker network ls -q --filter 'name=nook-iso-'                         # must be empty
lsof -nP -iTCP:<ISO_PORT> -sTCP:LISTEN -Fn                              # must print nothing
df -k /System/Volumes/Data                                              # two readings, both at least 5.5 GiB
shasum -a 256 …                                                         # package, pinned inputs, image ID check above
```

The generated `RUNID`, the three derived names and `<ISO_PORT>` are checked against these lists. Any hit, any port other than the authorized one, or `<ISO_PORT>` equal to `5432` or `5433`, stops the run.

### 4.2 Environment up (`env_up`: creates the run's own Docker resources)

```text
docker network create --driver bridge --label com.nook.disposable=true --label com.nook.iso-run=<RUNID> --label com.nook.package-manifest=<hash> nook-iso-net-<RUNID>
docker volume create  --label com.nook.disposable=true --label com.nook.iso-run=<RUNID> --label com.nook.package-manifest=<hash> nook-iso-vol-<RUNID>
# 0600 env file in the run directory: POSTGRES_USER=nook_iso_admin  POSTGRES_PASSWORD=<random>  POSTGRES_DB=postgres  POSTGRES_INITDB_ARGS=--auth-host=scram-sha-256
docker create --name nook-iso-pg-<RUNID> --pull never --network nook-iso-net-<RUNID> \
  --publish 127.0.0.1:<ISO_PORT>:5432 --mount type=volume,source=nook-iso-vol-<RUNID>,target=/var/lib/postgresql/data \
  --env-file <run dir>/secrets/iso.env --label … --restart no --memory 1g --pids-limit 512 --security-opt no-new-privileges <IMAGE_ID>
docker inspect <CID> --format '…'   # VERIFY BEFORE STARTING: image ID, exactly one network (ours), exactly one mount (ours), exactly one published port
                                    # (loopback, <ISO_PORT>), not privileged, no host mounts, no links, no volumes-from, expected labels
docker start <CID>
docker exec <CID> pg_isready -U nook_iso_admin -d postgres              # bounded retry loop
```

After each creation the new ID or name is recorded **before** the next step. The container is created and inspected **before it is started**, so a misconfiguration is caught while nothing is running.

### 4.3 Post-start proof of isolation (read-only)

```text
docker port <CID> 5432/tcp                                              # exactly 127.0.0.1:<ISO_PORT>
docker inspect <CID> --format '{{json .NetworkSettings.Ports}}'          # exactly {"5432/tcp":[{"HostIp":"127.0.0.1","HostPort":"<ISO_PORT>"}]}
docker inspect <CID> --format '{{json .NetworkSettings.Networks}}'       # only nook-iso-net-<RUNID>
docker inspect <CID> --format '{{range .Mounts}}…{{end}}'                # only nook-iso-vol-<RUNID>
lsof -nP -iTCP:<ISO_PORT> -sTCP:LISTEN -Fn                              # exactly n127.0.0.1:<ISO_PORT>
ipconfig getifaddr en0 || ipconfig getifaddr en1 ; nc -z -w 3 <that address> <ISO_PORT>     # must be refused
# admin path (inside the isolated container only):
#   databases are exactly "postgres"; roles are exactly "nook_iso_admin"; server_version starts with 17.11   # a fresh, empty cluster
```

### 4.4 Roles, database, beacon, then the tests

The `create` stage runs, through Class 2 inside the isolated container: `CREATE ROLE nook_migrator_test …`, `CREATE ROLE nook_app_test …`, `CREATE DATABASE nook_test OWNER nook_migrator_test TEMPLATE template0`, `ALTER DATABASE nook_test SET nook.iso_run_id = '<RUNID>'`, and the two `ALTER ROLE … PASSWORD` statements with statement logging switched off. The remaining stages are the revision 2 stages (`migrator_login`, `schema`, `provision`, `inventory`, `test_owner`, `test_app`, `test_tcp`, `drift`, `test_pool`) with the port and beacon changes in section 7.

### 4.5 Cleanup (identity-bound; only this run's resources)

```text
# 0. local files first: password files, env file, drift URL file (works even if Docker is unavailable)
# 1. snapshot disposable-role sessions inside the isolated cluster (INFO), then:
docker inspect <CID> --format '{{.Id}} {{index .Config.Labels "com.nook.iso-run"}}'     # must equal the record and <RUNID>; else NOT OURS, stop
docker stop --time 10 <CID>
docker rm <CID>                                  # never -f, never -v
docker volume inspect nook-iso-vol-<RUNID> --format '{{.Name}} {{.CreatedAt}} {{index .Labels "com.nook.iso-run"}}'   # must equal the record
docker volume rm nook-iso-vol-<RUNID>            # only after the container is gone
docker network inspect <NID> --format '{{.Id}} {{index .Labels "com.nook.iso-run"}} {{len .Containers}}'            # id+label match, zero attached
docker network rm <NID>
# 2. independent verification: nothing labelled com.nook.iso-run=<RUNID> remains (ps -a, volume ls, network ls); local files are gone;
#    the image is untouched; no other container, volume or network was named by this run.
```

Forbidden in every stage: `docker run`, `rm -f`, `kill`, `prune` of any kind, `compose`, `pull`, `system`, `cp`, `commit`, `exec` into any container other than `<CID>`, and any command built from a wildcard or command substitution over container lists.

## 5. Conditions that must hold, or the test stays blocked

| #   | Condition                                                                                             | How it is established                                                                                            |
| --- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| C1  | Docker is already running and the context is `desktop-linux` or `default`                             | `docker info`, `docker context show`; the runner never starts Docker                                             |
| C2  | The pinned image is present locally and equals the authorized image ID                                | `docker image inspect`; creation uses `--pull never`                                                             |
| C3  | No resource carrying the disposable label or the `nook-iso-` name prefix exists                       | the preflight lists above                                                                                        |
| C4  | `<ISO_PORT>` is not `5432` or `5433` and nothing listens on it                                        | constant check and `lsof`                                                                                        |
| C5  | The created container has exactly one network, one mount, one published loopback port, not privileged | `docker inspect` before `docker start`                                                                           |
| C6  | The only listener on `<ISO_PORT>` is `127.0.0.1` and the LAN address refuses it                       | `lsof`, `nc -z`                                                                                                  |
| C7  | The cluster is fresh and empty: one database `postgres`, one role `nook_iso_admin`, version 17.11     | Class 2 catalogue reads                                                                                          |
| C8  | Every test connection reaches the isolated database                                                   | beacon `nook.iso_run_id` equals the recorded `RUNID`                                                             |
| C9  | No credential or URL of the development database is present in the package, env files or processes    | static scan of the package for `nook_local_only`, `nook_dev` as a target, ports `5432`/`5433`; environment scrub |
| C10 | Disk is at least 5.5 GiB (two readings)                                                               | `df`                                                                                                             |
| C11 | Every Docker operation is from the closed list and names a recorded ID or exact name                  | structure of the runner, static scan                                                                             |
| C12 | Image ID, labels, IDs and volume `CreatedAt` match the records before each removal                    | `docker inspect` immediately before each `stop`/`rm`/`volume rm`/`network rm`                                    |

## 6. Failure and interruption handling

| Situation                                                                     | State                                     | Handling                                                                                                                                                                                                                                    |
| ----------------------------------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A condition C1–C4 fails                                                       | nothing created                           | Stop; the report names the condition                                                                                                                                                                                                        |
| `network create` or `volume create` fails                                     | possibly one resource                     | A pending record is written first; on failure the runner checks that exact name **and** run-id label; if present it is recorded and cleaned, if absent the pending record is removed                                                        |
| `docker create` fails or inspect shows a deviation                            | container exists but never started        | Cleanup removes it by recorded ID after the label check; nothing ran                                                                                                                                                                        |
| `docker start` or readiness fails                                             | container created                         | Cleanup stops and removes it, then the volume and network                                                                                                                                                                                   |
| A test stage fails                                                            | everything exists                         | The stage is not rerun in the same directory; `cleanup` then `report`                                                                                                                                                                       |
| Interrupt, terminate, hangup                                                  | any of the above                          | A trap runs the same identity-bound cleanup                                                                                                                                                                                                 |
| Docker becomes unavailable before cleanup                                     | resources may remain, running on loopback | Local secrets and env files are removed first; remote cleanup is reported **NOT VERIFIED**; nothing is claimed removed; the recovery stage lists labelled leftovers after Docker returns                                                    |
| Ambiguity (a resource has the right name but no matching label or record)     | unknown                                   | **NOT OURS / AMBIGUOUS**: reported, never touched. A resource carrying this run's exact random `RUNID` label can only have been created by this run, so one that lacks a record can be adopted for cleanup; this adoption is decision `I-9` |
| SIGKILL, host shutdown or sleep, crash between a Docker create and its record | leftovers                                 | Not preventable by traps; the recovery stage and the unique `RUNID` label make them findable and removable                                                                                                                                  |

## 8. Safety principles carried over, and risks that design alone cannot remove

| Principle                                   | How it holds in the isolated design                                                                                                                    |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Least privilege                             | `provision.sql` unchanged: runtime role has no `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER`; `INSERT`/`SELECT` only on `audit_events`; `TEMP` revoked |
| Independent manifest verification           | Still mandatory and documented; the token still binds the manifest                                                                                     |
| Explicit stage allow-list                   | Unchanged mechanism; `env_up` is a new stage that must be listed; `create` and `all` require `cleanup`                                                 |
| No overwriting of evidence                  | Unchanged: a stage with saved output is refused; a rerun needs a new run directory                                                                     |
| Identity-bound cleanup and recovery         | Stronger: IDs, labels and `CreatedAt` are checked before every removal; leftovers are findable by the unique `RUNID` label                             |
| Password redaction and local secret cleanup | Secrets (including the new env file) are removed first at cleanup; statement logging is switched off for the password statements                       |
| `INFO` is not acceptance                    | Unchanged: only `ENFORCE` results count                                                                                                                |

**Risks that cannot be eliminated by design alone.**

1. **The Docker socket is root-equivalent.** A bug in the runner could act on other containers. Mitigation is structural (closed operation list, recorded IDs, label checks, static scans), not absolute.
2. **Shared Docker VM resources.** The new container, its volume and `initdb` use disk, memory and CPU of the same VM as the development container. Earlier in this project free disk fell sharply when Docker started. Resource limits and the disk gate reduce, but do not remove, the chance of affecting the development environment.
3. **Host-gateway reachability.** On Docker Desktop a container can normally reach host services through the host gateway name. The isolated container could in principle reach `127.0.0.1:5433` on the host. It holds no development credentials and nothing in the package sends such traffic, but the network path exists and cannot be closed without an egress policy this design does not include.
4. **Same-user local access.** Any process of the same macOS user can reach the loopback port and read the 0600 files.
5. **Cleanup depends on Docker.** If Docker is unavailable at the end, the throwaway container may keep running (on loopback, with random credentials and no real data) until recovery.
6. **Shared image.** The image is reused read-only. Pinning by image ID detects substitution but not an image that is defective in both environments.
7. **Unobserved Docker behaviour.** Everything in section 10.

## 9. Manifest and hash plan

1. **Revision 2** stays in `docs/nook-phase-2/disposable-test/`, byte-for-byte, manifest `30df85941c508147452655b7f8582f82a176d16a024bdc764e253e97422f51b9`, as evidence of what was reviewed. It is not edited and not executed.
2. **Revision 3** would be written to a new folder (proposed `docs/nook-phase-2/disposable-test-isolated/`) from the four reusable files plus the eleven revised ones, with its own `MANIFEST.sha256`, a fresh static review, and a new owner review. Its hash is unknown until it exists.
3. **Token v3.** The runner's token becomes the SHA-256 of `manifest=<hash>;stages=<sorted list>;rundir=<path>;image=<IMAGE_ID>;port=<ISO_PORT>`, so the authorization also fixes the exact image and port.
4. **Independent verification** before every session stays mandatory (`shasum` on the manifest and every file, outside the runner).
5. Any change to any revision 3 file voids an authorization that quoted its old token.

## 10. Remaining unverified assumptions

Nothing here was observed. A first run may fail on any of them; a failure stops safely.

- Behaviour of these Docker CLI forms on this Docker Desktop version: `--pull never` with a locally present image, `--security-opt no-new-privileges` with the PostgreSQL entrypoint, `--memory`, `--pids-limit`, `--mount type=volume`, the label filters, and the `docker inspect` / `volume inspect` / `network inspect` format strings (`.Containers`, `.CreatedAt`, `.Labels`).
- That the local image tagged `postgres:17.11-alpine` has the ID the operator will pin, and that `POSTGRES_INITDB_ARGS=--auth-host=scram-sha-256` is accepted.
- That a connection arriving through Docker Desktop's port forwarding is subject to the `scram-sha-256` rule in the new container exactly as in the existing one.
- That `ALTER DATABASE … SET nook.iso_run_id` works for a custom setting without declaration, and that `current_setting` can read it as the roles.
- That a dedicated bridge network with a published loopback port works on this machine.
- The log-suppression settings, `psql` meta-commands, Prisma introspection by the runtime role, the `28P01` error code assumption and the `pg_stat_activity` query (all unchanged from revision 2).
- That resource limits are enough for `initdb` and the test load.
- The compose default network name of the existing environment (`nook_default`) is inferred, not observed.
