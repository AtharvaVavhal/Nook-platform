## 1. Purpose and the three levels of evidence

This plan tests the **draft nine-table schema** against PostgreSQL 17.11 in the existing Nook container, using only a disposable database and two disposable roles. It is not a production schema, and the SQL under test is kept outside the repository.

| Level                                    | Content                                                                                                                                                                                                                                                                                                                                                                                                         |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Demonstrated without a database          | **Verified** earlier in [local Phase 2 spike directory — second iteration] (network denied): the draft validates; `generate` and `migrate diff --from-empty` work offline; the default generator emits `.js` imports under the repo's `tsconfig`; the draft yields 9 tables, 5 enums, 10 foreign keys and 5 partial unique indexes. **Static** this task: the package's syntax, hashes and internal consistency (section 12) |
| Awaiting live disposable PostgreSQL test | **This package:** nullable composite foreign-key behaviour and column order; partial-index enforcement; drift; nine-table isolation; least-privilege behaviour; password authentication for both roles; shared-pool use of the adapter                                                                                                                                                                          |
| Not implemented                          | Everything in production: schema, migration, generator block, `DatabaseService` change, roles script, CI job, manifest and guard edits                                                                                                                                                                                                                                                                          |

**What a pass would not prove.** It would not approve the per-entity uniqueness scopes (`Q-4`), adopt the preview feature (`Q-4b`), give protection against table owners or superusers (`Q-6`), show that `A3` does or does not need a `nook_dev` run (`N-5`), or isolate reads (there is no row-level security). The tests, scripts and SQL have **never been executed**, so a first run may expose mistakes in them; a failure stops safely and cleanup is identity-bound.

**Gate (revision 2).** `run_disposable_test.sh` with no argument prints a "not authorized" banner and does nothing. Only `help` and `verify_package` run without a token. Every other stage requires **all** of:

1. an explicit stage name (no default; `all` is never implied);
2. `NOOK_ALLOWED_STAGES` listing that stage. Unknown names are refused. `all` runs only if it is **listed**, and then only if every stage it would run (`preflight` through `report`) is also listed; otherwise it is refused before any action. `create` and `all` also require `cleanup` to be listed;
3. `NOOK_DISPOSABLE_TEST_AUTH` equal to the SHA-256 of the exact text `manifest=<sha256 of MANIFEST.sha256>;stages=<allowed stages, sorted, unique, comma-joined>;rundir=<run directory>`. Changing the package, widening the stage list or changing the directory changes the token and is refused;
4. a run directory under `/private/tmp` or `/tmp`, named `disposable_pg_*`, outside the repository. For `preflight` and `all` it must **not exist yet**; for every other stage it must already exist.

**Evidence is never overwritten.** A stage that already has saved output is refused; a rerun needs a **new, separately reviewed run directory**, and therefore a new token. `cleanup`, `recover` and `report` may be repeated: their earlier output is moved aside under a timestamped name, never overwritten. Every invocation is appended to `records/authorizations.log`.

**Independent verification is mandatory.** The runner's own check is circular (it sits in the manifest it verifies). Before **every** session the operator must run `shasum -a 256 MANIFEST.sha256`, `shasum -a 256 -c MANIFEST.sha256` and a listing of the folder with ordinary tools, outside the runner, and compute the token the same way (commands are in the package README). `verify_package` is not a substitute.

**Suggested authorization wording (the owner decides, not this plan):** see section 6 of [the owner review](OWNER_REVIEW_SLICE_2_2.md); it lists the manifest hash, each permitted stage, the exact run directory and the token.

## 4. Objects, creation records, cleanup and recovery

| Object   | Name                 | Properties                                                                                                               | Record                     |
| -------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------- |
| Role     | `nook_migrator_test` | `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`; random password set after the negative login test | `records/role_….rec` (oid) |
| Role     | `nook_app_test`      | same attributes; random password                                                                                         | `records/role_….rec` (oid) |
| Database | `nook_test`          | owner `nook_migrator_test`, `TEMPLATE template0`                                                                         | `records/db_….rec` (oid)   |
| Files    | `secrets/*_pw`       | 0600, outside the repository, never printed                                                                              | removed first at cleanup   |

**Creation.** Immediately before each creation: an exact absence query (stop if present), then a pending record. Creation must succeed; attributes (or owner) are verified; the object's **oid** is written to the record; the pending record is removed.
**Cleanup** (`cleanup`, also run by the interrupt trap and by `all`): **first remove this run's local password and URL files**, whether or not the container is reachable; then load the recorded container ID and refuse if that exact container is not running (it reports "CLEANUP NOT PERFORMED REMOTELY", writes `remote_cleanup=NOT-VERIFIED` to `out/cleanup.status`, and tries nothing else, never claiming remote success); otherwise snapshot the disposable roles' sessions, drop the database and then the two roles **only if** a record exists and the live object has the same name and oid, using a statement that matches on both; then verify independently that only `nook_dev` and `postgres` remain, only `nook` remains as a non-system role, `nook_dev`'s oid, access list and connect flag are unchanged, and the retained volume exists.
**Ambiguity.** A same-named object with a different oid is **NOT OURS** and untouched; a pending record without a completed record is **AMBIGUOUS** and untouched; both are reported and give a non-zero result.
**Recovery** is a separate stage for leftovers from an earlier run directory. Without `NOOK_RECOVER_CONFIRM=drop-recorded-objects-only` it only lists records; it never drops anything without a matching record and never guesses.
**Limits of shell traps (unavoidable):** SIGKILL; host shutdown or sleep; a crash of the runner between a `CREATE` and the writing of its record (leaves a pending record); a terminal closed without a hangup signal; Docker becoming unavailable (cleanup then reports itself incomplete and does not switch containers). For these, only the documented recovery procedure applies, after separate authorization.

**Table-owner and superuser limit (`Q-6`).** The owner can update, delete, truncate, disable triggers on and drop `audit_events`, and a superuser bypasses everything; the runtime role can still **insert** forged rows. ## 7. Stages, commands and expected outcomes

Each stage is a separate process invocation with `NOOK_RUN_DIR`, `NOOK_ALLOWED_STAGES` and `NOOK_DISPOSABLE_TEST_AUTH` set. Each saves `out/<stage>.txt` and its true exit code `out/<stage>.rc`; a stage with existing output is refused. `all` (only if listed, with every constituent stage) runs them in order, stops at the first failing **prerequisite** stage (preflight through inventory), runs the independent test stages even if one fails, and **always** runs `cleanup` and `report`.

## 11. Consolidated stop conditions

Any of these stops the run (cleanup still runs where it applies): a package or pinned-input hash difference; an authorization token mismatch, a stage that is not in the authorized list, an `all` whose constituent stages are not all listed, `create` without an authorized `cleanup`; an unsafe, in-repository or (for `preflight`/`all`) already existing run directory; saved output already present for the stage; `DOCKER_HOST`, `DOCKER_CONTEXT` or `DOCKER_CONFIG` set, an unexpected Docker context; the container is not the exact expected container, image, compose project, healthy state, volume, or its identity changed since preflight; port mapping other than exactly `127.0.0.1:5433`, any other published port, a non-loopback listener, or no LAN address to test; a disk reading below 5.5 GiB; `db_guard.py` or the exact-URL check does not allow a target; any database other than `nook_dev` and `postgres`, or any role other than `nook`, before the run; any disposable object already existing; a failed or unconfirmed creation; a schema transaction failure; an inventory difference; any missing, duplicate, unexpected or failing result, or a suite that does not reach its end; any identity mismatch (`current_user`, `current_database()`); any Prisma command that mentions a shadow database; a password that does not appear as exactly 32 hexadecimal characters; any ambiguity.
