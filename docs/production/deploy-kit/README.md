# Nook production deploy kit

> **Not validated on live infrastructure.** Production Railway deployment, TLS against a Railway-hosted database, backups and
> restoration have **not** been validated on live Railway infrastructure. Everything here was exercised only against disposable local
> PostgreSQL 17 containers and the repository's automated tests. Treat each step as unverified on Railway and verify it yourself.

Scripts and SQL for provisioning and verifying a Nook PostgreSQL deployment. Each was tested against disposable local PostgreSQL 17 containers (up to 17.11, Debian build) serving a certificate chain of the same shape as Railway's PostgreSQL template: a leaf certificate (`CN=localhost`, with the service's private hostname among its subject alternative names) issued by a self-signed `root-ca`. `DB_CA_PEM` is the **root CA** certificate and `DB_CERT_SHA256` the **leaf** fingerprint (see the runbook, section 3).

## TLS findings (installed `pg` 8.16.3 / `pg-connection-string` 2.14.1, Prisma 7.10.1)

- `pg`: with no `sslrootcert`, `sslmode=require` and `verify-full` **reject** a certificate from a private CA (the system trust store does not contain it). `uselibpqcompat=true&sslmode=verify-ca&sslrootcert=<root CA file>` **connects over TLS 1.3 with the right CA and rejects a wrong one**, and skips the hostname check (libpq `verify-ca` semantics). `sslmode=verify-full&sslrootcert=<root CA file>` also verifies the hostname against the certificate's names: a matching DNS name connects and any other DNS name is refused. **With an IP-address host the `pg` driver does not verify the hostname**, so never put an IP address in `DATABASE_URL`.
- A URL with **no TLS parameter connects in plaintext** and the app still reports healthy. Production must carry the TLS parameters, and the server should reject non-TLS (`hostnossl ... reject`) or the app should refuse such a URL at start-up (code change, not made).
- **Prisma migration engine**: `sslmode=require` and `verify-full` connect **without verifying** the certificate; `sslaccept=strict` **rejects** the self-signed certificate **even when `sslcert` is given the exact certificate** (`sslcert` is not a trusted-root setting). Prisma 7.10.1's `prisma.config.ts` has no adapter or engine option, so migrations cannot use the `pg` TLS path. **Prisma cannot verify the template's self-signed certificate with any available setting.**

## Solved since the first rehearsal

- **Prisma migrations with authenticated TLS:** `scripts/ops/migrate-with-tls-proxy.ts` runs the real `prisma migrate deploy` through `scripts/ops/pg-tls-proxy.ts`, which pins the CA **and** the SHA-256 fingerprint, rejects expired/changed certificates and plaintext upstreams, and listens on loopback only. Wrong pin, wrong CA or an unreachable port: exit 3, **nothing migrated**. Correct pin: 24 migrations finished, `migrate status` up to date, server log shows TLSv1.3.
- **Plaintext fallback:** the API refuses to start in production unless `DATABASE_URL` demands verified TLS (`apps/api/src/config.ts`); PostgreSQL-side `hostnossl all all all reject` is applied and checked with `require_tls.sh` (non-TLS refused, wrong CA refused, wrong password refused, correct TLS accepted; verified locally, runbook section 3.3).

See the disclaimer at the top: nothing in this folder has been validated on live Railway infrastructure.
