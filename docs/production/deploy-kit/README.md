## TLS findings (installed `pg` 8.16.3 / `pg-connection-string` 2.14.1, Prisma 7.10.1)

- `pg`: `sslmode=require` and `verify-full` **reject** a self-signed certificate. `uselibpqcompat=true&sslmode=verify-ca&sslrootcert=<file>` **connects over TLS 1.3 with the right certificate and rejects a wrong one**, and skips the hostname check (needed because the template certificate is `CN=localhost`).
- A URL with **no TLS parameter connects in plaintext** and the app still reports healthy. Production must carry the TLS parameters, and the server should reject non-TLS (`hostnossl ... reject`) or the app should refuse such a URL at start-up (code change, not made).
- **Prisma migration engine**: `sslmode=require` and `verify-full` connect **without verifying** the certificate; `sslaccept=strict` **rejects** the self-signed certificate **even when `sslcert` is given the exact certificate** (`sslcert` is not a trusted-root setting). Prisma 7.10.1's `prisma.config.ts` has no adapter or engine option, so migrations cannot use the `pg` TLS path. **Prisma cannot verify the template's self-signed certificate with any available setting.**

## Solved since the first rehearsal

- **Prisma migrations with authenticated TLS:** `scripts/ops/migrate-with-tls-proxy.ts` runs the real `prisma migrate deploy` through `scripts/ops/pg-tls-proxy.ts`, which pins the CA **and** the SHA-256 fingerprint, rejects expired/changed certificates and plaintext upstreams, and listens on loopback only. Wrong pin, wrong CA or an unreachable port: exit 3, **nothing migrated**. Correct pin: 24 migrations finished, `migrate status` up to date, server log shows TLSv1.3.
- **Plaintext fallback:** the API refuses to start in production unless `DATABASE_URL` demands verified TLS (`apps/api/src/config.ts`); PostgreSQL-side `hostnossl all all all reject` was tested (non-TLS refused, wrong CA refused, wrong password refused, correct TLS accepted).
